# 주차별 보안 요구사항

매주 아래 요구사항을 만족하도록 게시판을 고칩니다.
교수님은 학기 말에 모든 팀의 게시판을 **같은 테스트**로 확인합니다.
테스트의 정확한 입력값은 공개하지 않지만, 무엇을 확인하는지는 여기 적힌 그대로입니다.

> **정상 기능도 함께 테스트합니다.**
> 모든 요청을 막아 버리면 보안 테스트는 통과해도 정상 기능 테스트에서 점수를 잃습니다.

## 매주 보고서에 들어갈 것 (항목마다)

1. **외부입력**: 사용자가 바꿀 수 있는 값은 무엇이고 어디로 들어오나 (`req.query`, `req.params`, `req.body`, 쿠키, 파일)
2. **문제 코드**: 파일 이름과 줄 번호
3. **고치기 전 증거**: 문제가 실제로 일어나는 요청과 응답
4. **수정 코드**와 그렇게 고친 이유
5. **고친 후 결과**: 같은 요청을 다시 보냈을 때의 응답
6. **이 줄을 지우면?**: 내가 넣은 방어 코드를 지우면 어떤 문제가 다시 생기나
7. **AI 사용 메모**: AI가 제안했지만 고치거나 버린 부분과 그 이유 (한 줄이면 충분)

---

## 9주차 · 구조 익히기

- 게시판을 실행하고 GitHub 저장소를 만듭니다.
- 게시글 검색, 로그인, 관리자 기능의 코드 위치를 찾습니다.
- 이상해 보이는 코드 3곳을 표시합니다. (아직 고치지 않습니다)

## 10주차 · 입력값 검증, SQL Injection, XSS

| 번호 | 요구사항 |
|---|---|
| R10-1 | 사용자 입력으로 SQL 명령의 의미를 바꿀 수 없어야 합니다. (모든 SQL) |
| R10-2 | 번호 자리(`:id` 등)에는 양의 정수만 받습니다. 아니면 400. |
| R10-3 | 문자열 자리에는 문자열만 받습니다. (객체나 배열이 오면 400) |
| R10-4 | 길이 제한: 제목 1~100자, 본문 1~5000자, 댓글 1~500자, 이름 1~30자. 어기면 400. |
| R10-5 | 게시글 본문, 제목, 검색어가 화면에 나올 때 스크립트가 실행되지 않아야 합니다. |
| R10-6 | 단, 본문의 `<b>`, `<i>`, `<u>`, `<br>` 태그는 계속 굵게/기울임 등으로 보여야 합니다. |

## 11주차 · 로그인과 비밀번호

| 번호 | 요구사항 |
|---|---|
| R11-1 | 비밀번호는 bcrypt 같은 비밀번호 전용 해시로 저장합니다. (MD5 금지) |
| R11-2 | 비밀번호는 8자 이상이어야 합니다. 아니면 400. |
| R11-3 | 로그인 실패 메시지는 "이메일 또는 비밀번호가 올바르지 않습니다"처럼 하나로 통일하고, 입력한 비밀번호를 응답에 담지 않습니다. |
| R11-4 | 같은 계정으로 5번 연속 실패하면 5분 동안 그 계정의 로그인을 막습니다. (429) |
| R11-5 | 로그인하지 않은 사람은 글쓰기·수정·삭제, 댓글 쓰기·삭제, 파일 올리기를 할 수 없습니다. (401) |
| R11-6 | 기본 계정도 새 해시 방식으로 로그인할 수 있어야 합니다. (`npm run db:reset` 후에도) |

## 12주차 · 권한

| 번호 | 요구사항 |
|---|---|
| R12-1 | 글과 댓글은 쓴 사람 또는 관리자만 수정·삭제할 수 있습니다. (403 또는 404) |
| R12-2 | 글쓴이는 로그인한 사람으로 정해집니다. 보낸 값에 다른 사람 번호가 있어도 무시합니다. |
| R12-3 | 관리자 여부는 서버가 세션으로 판단합니다. 주소나 보낸 값에 들어 있는 권한 정보는 믿지 않습니다. |
| R12-4 | 관리자 기능은 모두 관리자만 쓸 수 있습니다. (403) |
| R12-5 | 관리자 회원 목록에 비밀번호 해시가 들어가지 않습니다. |
| R12-6 | 화면에서 버튼을 숨기는 것은 보안이 아닙니다. 서버에서 반드시 확인합니다. |

## 13주차 · 세션, 쿠키, CSRF, 오류 처리

| 번호 | 요구사항 |
|---|---|
| R13-1 | 로그인에 성공하면 세션 ID를 새로 발급합니다. |
| R13-2 | 로그아웃하면 그 세션은 다시 쓸 수 없습니다. |
| R13-3 | 세션 쿠키에 `HttpOnly`, `SameSite=Lax`(또는 `Strict`)를 설정합니다. `Secure`는 운영 환경에서만 켜도록 코드에 작성합니다. |
| R13-4 | 사용자 정보를 쿠키에 따로 저장하지 않습니다. |
| R13-5 | `docs/API.md`의 CSRF 토큰 약속을 구현합니다. 토큰이 없거나 틀린 상태 변경 요청은 403. |
| R13-6 | 오류가 나도 응답에 stack, 파일 경로, SQL 문장, DB 오류 내용이 나오지 않습니다. |
| R13-7 | 서버 로그에 비밀번호, 세션 ID가 남지 않습니다. |
| R13-8 | `/api/health`는 `{ ok: true }`만 돌려줍니다. |
| R13-9 | 세션 비밀값과 DB 비밀번호가 코드에 직접 적혀 있지 않습니다. (`.env`가 없으면 서버가 켜지지 않아도 됩니다) |

## 14주차 · 첨부파일 + 전체 재검사

| 번호 | 요구사항 |
|---|---|
| R14-1 | 파일 크기는 5MB까지. 넘으면 400 또는 413. |
| R14-2 | 허용 확장자: jpg, jpeg, png, gif, pdf, txt. 나머지는 400. |
| R14-3 | 저장 파일 이름은 서버가 만듭니다. 사용자가 보낸 파일 이름을 저장 경로에 쓰지 않습니다. |
| R14-4 | 업로드 응답에 서버의 실제 폴더 경로가 나오지 않습니다. |
| R14-5 | 업로드 폴더 밖의 파일은 절대 내려받을 수 없습니다. |
| R14-6 | 로그인한 사람만 내려받을 수 있습니다. 첨부파일이 붙은 글을 볼 수 있는 사람이 내려받을 수 있습니다. |
| R14-7 | 내려받을 때 브라우저가 파일을 열지 않고 저장하도록 합니다. (`Content-Disposition: attachment`) |
| R14-8 | 10~13주차 요구사항이 모두 여전히 지켜져야 합니다. |

## 15주차 · 발표와 개인 Code Defense

교수님이 내 코드에서 한 곳을 골라 질문합니다.

- 외부입력은 어디인가?
- 어떤 공격이 가능한가?
- 지금 방어는 어디에 적용되어 있는가?
- 이 코드 한 줄을 지우면 어떤 문제가 다시 생기는가?
- 다른 방법으로 구현한다면?
